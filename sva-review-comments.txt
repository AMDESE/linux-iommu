[Severity: High]
Could the PerfOpt re-attach keep the identity DTE on the passthrough
path?

amd_iommu_enable_perfopt() sets dev_data->perfopt and detaches then
re-attaches the device to the identity domain.  attach_device() skips
the old GCR3 setup for that re-attach, but the new probe-time allocation
means gcr3_info->gcr3_tbl is already non-NULL.

pdom_is_sva_capable() returns true for the identity domain, so
set_dte_entry() now calls set_dte_gcr3_table() and sets DTE_FLAG_GV
instead of calling set_dte_passthrough().  This contradicts the PerfOpt
path's requirement that the device remain untranslated with PASID, ATS,
and PRI disabled.  Before this patch, the skip_caps jump also skipped
init_gcr3_table(), so the identity DTE took set_dte_passthrough().

[Severity: High]
Can a reset restore distinguish an SVA domain whose mm notifier has
already released?

pci_dev_reset_iommu_prepare() removes the PASID from the driver list.
If mmu_notifier_release() then runs, sva_mn_release() sees no entry to
disable and the notifier is removed before the page tables are freed.

pci_dev_reset_iommu_done() subsequently invokes this path with the
blocking domain.  iommu_sva_set_dev_pasid() accepts it and writes
domain->mm->pgd back to GCR3 without an active notifier.  The device can
then resume DMA through page tables that exit_mmap() is freeing.

[Severity: High]
Could release_device() free the GCR3 table after the core has selected the
identity release domain?

iommu_deinit_device() switches a require_direct device to identity_domain
instead of blocked_domain.  amd_iommu_attach_device() then returns early
when the device is already attached to that identity domain, leaving its
GCR3-mode DTE unchanged.

amd_iommu_release_device() warns that dev_data->domain is still set and
then frees gcr3_tbl.  The retained DTE can therefore reference the freed
table.  On a later rescan, the reused dev_data is still attached to the
identity domain, so the early return also prevents the DTE from being
rewritten for the newly allocated table.
